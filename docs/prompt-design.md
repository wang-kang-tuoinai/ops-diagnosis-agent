# 诊断提示词与回归方法

正式入口 `langgraph_agent_msgstream.py` 从 `system_prompt.py` 导入 SYSTEM_PROMPT，HTTP 后端也使用同一诊断图。其他旧实验脚本暂不迁移，不是当前服务端入口。

## 本次依据

通过本地会话历史 API 只读抽查最近三个诊断会话的用户问题、工具调用参数和回答。该接口读取 MySQL 展示记录，没有发起新诊断、修改历史或导出原始会话到仓库。

已有回答通常能完成统计、请求采样、Trace 下钻和知识检索；需要改进的是从有限证据到结论的跨度：

| 原回答中出现的判断模式 | 提示词要求 |
| --- | --- |
| 少量成功 SQL 就称 MySQL 全程健康 | 限定为已查看样本，不能推出整个窗口健康 |
| 19 秒与 55 秒窗口直接比较错误数量并称恶化 | 说明窗口长度、样本量和采集口径，比较可比比例与分布 |
| 两个错误相隔约一秒，推出只是短时抖动 | 仅描述采集到的时间分布，持续性需要更广窗口证据 |
| hello 超时，进而判断连接池耗尽；self_ms 被归为等待连接 | 区分失败环节与底层原因，self_ms 不代表具体执行内容 |
| 没有 MySQL Span，直接断言数据库绝未改动 | 结合链路完整性、显式属性和项目路径，标明证据边界 |
| 发布失败，直接称消息永久丢失、邮件未送达 | 区分应用报告发布失败与最终投递结果，核对确认机制和下游证据 |
| 高频同用户更新，直接称超高并发/重试风暴 | 请求频率与并发不是一回事，异常请求模式不等于攻击归因 |
| 检索 query 带入未经验证的连接池耗尽等原因 | 检索以事实为主，候选原因作为待验证问题 |

这些规则不预设“本次一定是 Redis 暂停或 MySQL 行锁”，也不把演练时间线当成 Agent 可见答案。业务特定的超时、回源和 MQ 重连语义继续由知识库提供。

## 提示词职责

范围与时间、渐进下钻、证据口径、知识引用、能力边界、简洁回答。工具的详细参数与上限仍以各工具描述为准。

对于系统规则，模型每次收到且只收到一条当前部署的 SystemMessage；CLI/checkpoint 中保存的旧 SystemMessage 仅在本次模型输入中被替换，不重写历史。按用户轮次裁剪的逻辑和工具调用/返回配对保留。

升级镜像后新旧会话的下一轮都会应用新版提示词；已经生成的回答不会重新生成，也不是修改文件后立即改变正在运行容器。

```powershell
# 在 ops-agent 根目录，依赖已经运行时
docker compose up -d --build --no-deps ops-diagnosis-agent
```

## 验证

```powershell
# 在 ops-diagnosis-agent 目录
.\.venv\Scripts\python.exe -m unittest test_system_prompt test_backend test_log_tools test_trace_tools test_rag_tools -q
```

新增测试覆盖同步、异步模型输入、旧 checkpoint 的系统规则更新、不改写持久化历史及工具消息配对。模拟工具返回中含指令文本时，验证它仍作为 ToolMessage 传入；这不证明真实模型能在所有情况下抵御提示注入。

自动测试不使用真实模型，不能证明诊断准确率提高。建议用仍可查询的演练窗口，或今后保存的脱敏工具结果固定样本，人工比较以下场景：

| 场景 | 主要验收点 |
| --- | --- |
| Redis 短暂停顿 | 能确认读/握手超时及接口影响，不把连接池耗尽写成事实 |
| MySQL 局部慢请求 | 包含 ok 慢请求下钻；确认慢 SQL，锁等待仍作为待验证原因 |
| RabbitMQ 发布失败但 HTTP 200 | 区分 HTTP、发布和消费结果，不直接宣称永久丢失 |
| 热点写/锁冲突 | 区分 409 竞争、Redis 基础设施错误及攻击猜测 |
| 不同长度窗口追问 | 不只按原始数量判断恶化，不继承上一窗口的根因 |
| 工具失败/数据截断 | 明确限制；必要时聚焦/分段，不宣称全量或正常 |
| 纯项目知识问题 | 直接检索并引用有效 K 引用，无需查询现场统计 |

检查工具调用是否必要、时间和服务范围是否一致、数字是否有来源、推断是否在对应结论附近标注，以及回答是否直接回应问题。不要把措辞变谨慎本身当成诊断质量提高，也不要仅为缩短回答而省略关键证据。
